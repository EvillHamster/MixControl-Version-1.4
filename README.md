# MixControl Version 1.6

Версия для **Microsoft SQL Server 2019** (уровень совместимости базы **150**) и **Node.js 22.14.0**. Рабочая установка на Windows Server не требует Docker или PostgreSQL. [MixControl 1.3](https://github.com/EvillHamster/MixControl---V1.0/tree/v1.3) остаётся в прежнем репозитории и использует свою базу.

Фронтенд: React 19, TypeScript, Vite и Tailwind, папка src/. Сервер: Express, TypeScript и драйвер mssql, папка server/. Express обслуживает API и собранный фронтенд с одного адреса. Схема и триггеры T-SQL находятся в [server/mssql](server/mssql). SQL Server рассчитывает OK/NOK по обеим температурам и ведёт корректировки. Сервер формирует ежедневные отчёты по московскому времени. Для SSE он отслеживает пять счётчиков изменений на экземпляр приложения; данные появляются в других вкладках после фиксации транзакции.

Вход сохраняется после закрытия браузера и перезапуска сервера. Сессии не имеют серверного срока окончания и завершаются при выходе, удалении или блокировке аккаунта, а также при изменении данных входа. Браузерная cookie продлевается при использовании приложения; очистка cookies потребует повторного входа.

## Изменения в версии 1.6

- Разрешены повторные SUP: каждая попытка сохраняется как отдельное измерение. SUP по-прежнему состоит из 7 цифр.
- Сотрудник может исправлять SUP и смесь только своих записей. Сохранённые температуры, чужие записи и удаление остаются недоступны.
- Импорт журнала обновляет измерение только по внутреннему ID; без ID создаётся новая попытка. Экспорт содержит столбец «ID измерения».
- Добавлено руководство по F1 для EMPLOYEE, ADMIN и KEYUSER: Escape закрывает справку, открытые формы сохраняются. До входа F1 не перехватывается.
- Добавлен favicon. Исправлены выравнивание таблиц и вкладок, столбец «Действия», подсказки и лишние декоративные значки в формах.

Миграция 006 автоматически снимает только уникальность SUP и создаёт обычный индекс. Пользователи, измерения, история и связи сохраняются. Старые незавершённые предпросмотры импорта нужно загрузить повторно.

## Изменения в версии 1.5

Добавлены фильтр линий MB/FMF, индивидуальная и общая очистка фильтров, единые кнопки очистки и подсветка обязательных полей. Исправлены проверка идентификаторов SQL Server, допустимые символы логинов и скачок журнала после сохранения. Корректировки сохраняются после удаления исходного измерения; удалять их может только KEYUSER.

Обновление существующей установки: остановите приложение, обновите код, выполните npm.cmd ci --include=dev и npm.cmd run build, затем запустите npm.cmd start. Сохраните свой .env и существующую базу. Новые миграции применяются автоматически; создавать базу заново или повторно импортировать данные не нужно.

## Обновление работающего сервера Windows

Эти шаги подходят, если MixControl уже работает на Windows Server с SQL Server 2019. Используйте Node.js **22.14.0**. Адрес сайта, настройки IIS и существующая база остаются прежними.

1. Остановите запущенное приложение: при ручном запуске нажмите **Ctrl+C** в его консоли; при запуске службой или Планировщиком остановите соответствующую службу или задание. SQL Server оставьте включённым.

2. Откройте PowerShell в папке установленного приложения. Ниже замените `C:\Apps\MixControl` на фактический путь рабочего сервера. Сохраните действующий `.env`: он содержит подключение к вашей рабочей базе.

```powershell
Set-Location 'C:\Apps\MixControl'
$ErrorActionPreference = 'Stop'
node --version
if ((node --version) -ne 'v22.14.0') { throw 'Для проекта требуется Node.js 22.14.0' }

New-Item -ItemType Directory -Path 'C:\MixControl-backups' -Force | Out-Null
$backupStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
npm.cmd run db:snapshot -- export "C:\MixControl-backups\before-norm-update-$backupStamp.json"
if ($LASTEXITCODE -ne 0) { throw 'Резервная копия не создана — обновление остановлено' }
```

Снимок сохраняет рабочие данные и хеши паролей; храните его вне папки сайта и репозитория. Для штатного резервирования SQL Server также можно использовать полную резервную копию базы в SSMS.

3. Получите **текущую ветку main**, установите зависимости и соберите приложение. Старый архив релиза `v1.6` не содержит исправлений, опубликованных после создания этого тега.

```powershell
git status --short
git pull --ff-only origin main
if ($LASTEXITCODE -ne 0) { throw 'Код не обновлён — дальнейшие команды не выполняйте' }

npm.cmd ci --include=dev
if ($LASTEXITCODE -ne 0) { throw 'Ошибка установки зависимостей' }

npm.cmd run build
if ($LASTEXITCODE -ne 0) { throw 'Ошибка сборки' }

npm.cmd run db:migrate
if ($LASTEXITCODE -ne 0) { throw 'Ошибка миграции базы' }
```

Если папка установлена из ZIP и не содержит `.git`, получите актуальный код кнопкой **Code → Download ZIP** на странице ветки **main**, распакуйте в новую папку и скопируйте в неё свой действующий `.env`. Остановив прежний экземпляр, выполните в новой папке команды `npm.cmd ci --include=dev`, `npm.cmd run build` и `npm.cmd run db:migrate` из шага 3. Службе или заданию укажите новую рабочую папку. Используется прежняя база из `.env`; создавать её повторно или восстанавливать снимок для обычного обновления не требуется.

4. Запустите приложение прежним способом. Для ручного запуска:

```powershell
npm.cmd start
```

Для постоянной работы используйте уже настроенную службу или задание Планировщика вместо второго ручного экземпляра. Для рабочей эксплуатации предназначен `npm.cmd start`.

5. В другом окне PowerShell, из папки проекта, проверьте доступность API. Команда читает фактический PORT из `.env`:

```powershell
$apiPort = node --input-type=module -e "import 'dotenv/config'; process.stdout.write(process.env.PORT || '3001')"
Invoke-RestMethod "http://127.0.0.1:$apiPort/api/health"
```

Должен вернуться `status: ok`. Эта проверка рассчитана на обычное подключение приложения к `127.0.0.1` или `0.0.0.0`; при другом HOST используйте указанный в нём адрес. Затем откройте привычный адрес сайта, обновите страницу **Ctrl+F5** и войдите с рабочими данными учётной записи.

**Что изменится в базе:** миграция **007** при первом запуске приведёт нормативы старых измерений к текущим лимитам их смесей. OK/NOK и отчёты пересчитаются; фактические температуры, SUP, даты и авторство сохранятся. Следующие изменения лимитов будут автоматически обновлять все связанные измерения. Для проверки выберите запись существующей смеси и сравните её лимиты с каталогом; прежние и новые нормативы доступны в техническом аудите.

Для новой установки с нуля используйте следующий раздел «Установка на Windows Server».

## Установка на Windows Server

1. Установите Git и [Node.js 22.14.0 x64](https://nodejs.org/dist/v22.14.0/node-v22.14.0-x64.msi). Для SQL Server нужен TCP-порт экземпляра, обычно 1433. Для именованного экземпляра укажите его фактический TCP-порт. Службы приложению достаточно с логином SQL Server в отдельной базе; права sysadmin ему не нужны. Если у вас разрешена только Windows Authentication, согласуйте с ИТ отдельный SQL-логин перед установкой: текущая конфигурация использует SQL Server Authentication.
2. Через SSMS администратор создаёт отдельную базу и логин. Можно выполнить следующий T-SQL; замените пароль, не сохраняйте его в репозитории:

```sql
USE master;
GO
CREATE DATABASE MixControl14;
GO
ALTER DATABASE MixControl14 SET COMPATIBILITY_LEVEL = 150;
GO
CREATE LOGIN mixcontrol_app WITH PASSWORD = N'REPLACE_WITH_STRONG_PASSWORD', CHECK_POLICY = ON;
GO
USE MixControl14;
GO
CREATE USER mixcontrol_app FOR LOGIN mixcontrol_app WITH DEFAULT_SCHEMA = dbo;
ALTER ROLE db_owner ADD MEMBER mixcontrol_app;
GO
```

Роль db_owner относится только к базе MixControl14 и нужна учётной записи для запуска миграций и восстановления. Откройте TCP-порт SQL Server только для сервера приложения, если СУБД расположена на другой машине. Для рабочего подключения настройте сертификат, которому доверяет сервер приложения, и используйте в SQLSERVER_HOST имя из сертификата.

3. В PowerShell:

```powershell
git clone https://github.com/EvillHamster/MixControl-Version-1.4.git MixControl-1.6
Set-Location .\MixControl-1.6
node --version
npm.cmd ci --include=dev
Copy-Item .env.example .env
notepad .env
```

Проверьте, что node --version показывает v22.14.0. В .env заполните SQLSERVER_HOST, SQLSERVER_PORT, SQLSERVER_DATABASE, SQLSERVER_USER и SQLSERVER_PASSWORD. Пароль вводится обычным значением, URL-кодирование не требуется. Если в пароле есть # или пробелы, заключите значение в кавычки по правилам dotenv. SQLSERVER_TRUST_CERTIFICATE=false оставьте для работы с проверяемым сертификатом. На изолированном тестовом сервере с самоподписанным сертификатом можно временно указать true.

```powershell
npm.cmd run db:migrate
npm.cmd run build
npm.cmd start
```

Из другого окна PowerShell выполните:

```powershell
Invoke-RestMethod http://127.0.0.1:3001/api/health
```

После ответа status: ok откройте http://127.0.0.1:3001 на сервере. Если переносите данные, сначала выполните инструкции ниже. Для пустой новой установки при первом входе предложит создать единственного KEYUSER.

4. Настройте запуск при старте Windows под отдельной учётной записью. В Планировщике заданий укажите cmd.exe с аргументами /c npm.cmd start и каталог приложения как рабочую папку; настройте выполнение без входа пользователя, отключите ограничение времени работы и включите перезапуск при сбое. Node.js должен быть в PATH этой учётной записи. У неё должны быть права чтения каталога и .env, но доступ к .env не нужен сотрудникам. Убедитесь, что SQL Server успевает запуститься, или задайте задержку запуска и повторные попытки.
5. Для сотрудников проксируйте внутренний HTTPS-адрес на 127.0.0.1:3001 через IIS с URL Rewrite/ARR или другой корпоративный прокси. Сохраняйте исходный Host и отключите буферизацию SSE на /api/events. Включите COOKIE_SECURE=true и, при одном доверенном прокси, TRUST_PROXY=1; перезапустите приложение. Для разработки с уже доступной тестовой SQL Server есть npm.cmd run dev; это режим Vite, не рабочий запуск.

## Перенос данных из 1.3

1. В исходной папке версии 1.3 с подключением к её базе сделайте свежий снимок. Для финального переключения сначала приостановите ввод в 1.3: изменения после снимка в 1.4 не попадут.

```powershell
node scripts/database-snapshot.mjs export 'C:\SecureTransfer\mixcontrol-13.json'
```

2. В папке 1.4 направьте .env на **пустую** SQL Server, примените миграции и восстановите снимок. До восстановления не создавайте пользователей через интерфейс.

```powershell
npm.cmd run db:migrate
npm.cmd run db:snapshot -- restore 'C:\SecureTransfer\mixcontrol-13.json'
npm.cmd start
```

Переносятся пользователи с хешами паролей, смеси, измерения со своими ID и историческими нормативами, аудит, корректировки, их история и отчёты. Существующие исторические SUP сохраняются; новые значения по-прежнему проверяются. Входите с прежними логином и паролем. Сессии и незавершённые предпросмотры импорта не переносятся. Скрипт отклоняет восстановление при наличии данных в целевой базе и отменяет транзакцию, если вычисленный OK/NOK отличается от снимка.

Снимок содержит рабочие данные, не добавляйте его в Git. Сверьте число измерений, пользователей, выборочные отчёты и корректировки перед переключением сотрудников. Для резервных копий новой рабочей базы используйте штатное резервное копирование SQL Server (.bak); переносимый снимок можно создать командой npm.cmd run db:snapshot -- export <файл.json>.

```powershell
npm.cmd test
npm.cmd run build
```

Сквозные тесты используют две отдельные **пустые** базы SQL Server 2019 с совместимостью 150. Направьте SQLSERVER_HOST, SQLSERVER_PORT и учётные данные на тестовый экземпляр, оставьте SQLSERVER_DATABASE=master, задайте SQLSERVER_TEST_DATABASE и SQLSERVER_TEST_RESTORE_DATABASE (имена с префиксом MixControlTest_) и выполните npm.cmd run test:integration. Тесты откажутся работать в непустой первой базе; вторая проверяется перед использованием. После прогона данные остаются в этих тестовых базах для диагностики. Для ручной проверки с синтетическими данными соберите фронтенд, настройте SQLSERVER_* на тестовый экземпляр, разрешите создание временных баз через переменную SQLSERVER_ALLOW_TEMP_DATABASES=true и запустите node --import tsx scripts/ui-check.mjs. Адрес и тестовый пароль появятся в консоли. Введите stop для удаления созданной скриптом базы.

## Сохранение корректирующих действий

Корректировки и их история сохраняются при обычном и массовом удалении измерений из журнала. В карточке и списке отмечается, что исходная запись удалена; прежний внутренний ID остаётся в истории. Исправление температур также не удаляет корректировку автоматически. Удаление из активных или архива доступно только KEYUSER, с подтверждением и записью в техническом аудите. ADMIN сохраняет просмотр и редактирование, но не может удалять корректировки.

Миграция 004 применяется автоматически при запуске обновлённого сервера и сохраняет существующие данные. Ранее удалённые корректировки сама миграция не восстанавливает.

В форме измерения обязательны SUP, выбор смеси, T(fact) и T(обор). Незаполненные и некорректные поля подсвечиваются красным, сохранение заблокировано до их заполнения. Сервер и импорт также проверяют наличие обеих температур. Результат — OK или NOK; старые неполные измерения сохраняются без изменения данных.

## Повторные измерения и исправление реквизитов

SUP состоит из 7 цифр и может повторяться. Каждая попытка, в том числе повтор после NOK, получает отдельный внутренний ID. Поиск SUP показывает все попытки; изменение и удаление выполняются по ID выбранного измерения. Миграция 006 снимает только уникальность SUP и создаёт обычный индекс поиска, сохраняя измерения, связи, историю и уникальность остальных ID. Она применяется автоматически при запуске; старые незавершённые предпросмотры импорта нужно загрузить заново.

Сотрудник может исправить SUP и смесь только в собственных записях. Температуры, дата, автор и удаление ему недоступны. Изменение смеси подставляет её нормативы для этой записи и пересчитывает OK/NOK по прежним температурам. При исправлении только SUP исторические нормативы не меняются. ADMIN и KEYUSER сохраняют прежние права. Версия записи защищает от одновременного изменения, технический аудит фиксирует исправления.

Импорт журнала: без столбца «ID измерения» или с пустым ID строка всегда добавляет новое измерение. Повторные SUP в одном файле разрешены. Для обновления выгрузите журнал, сохраните ID нужной строки и импортируйте исправления с этим ID. Несуществующий, некорректный или повторяющийся в файле ID отклоняется; неоднозначного обновления по SUP больше нет. Для новой строки обязательны обе температуры; при обновлении без столбца T(обор) сохраняется прежнее значение. Итог из Excel не принимается на доверие и рассчитывается сервером.

## Обновление лимитов смеси

Изменение T min / T max в базе смесей обновляет нормативы всех связанных измерений, включая старые записи и повторные SUP. OK/NOK рассчитывается заново по обеим фактическим температурам; фактические значения, даты, авторство и идентификаторы сохраняются. Ежедневные отчёты пересчитываются по обновлённым данным, другие открытые окна получают уведомление об изменении. Прежние и новые лимиты и результаты сохраняются в техническом аудите.

Миграция 007 применяется автоматически при запуске и один раз приводит старые нормативы журнала к текущему каталогу смесей. После этого синхронизация работает при редактировании, импорте и непосредственном изменении лимитов в SQL Server. Права пользователей, правила корректирующих действий и проверка допустимого диапазона не меняются. При восстановлении резервной копии её содержимое сохраняется без пересчёта.
